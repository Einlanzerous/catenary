All six subtasks are closed with their evidence on the ticket. IDEA-23 itself stays open, because closing the spike means deciding whether to graduate to a project and a repo — and that is a judgement, not a measurement.

R1

The socket survives, and a forced kill resumes clean

Two clients, 80 minutes, same server, same tunnel. They differ in exactly one thing: whether the application-level heartbeat is running.

[hb]   DONE total=1h20m0s reconnects=0  longest_single_socket=1h20m0s
[nohb] DONE total=1h20m0s reconnects=35 longest_single_socket=2m5s

The heartbeat client's socket was closed by the test's own deadline expiring, not by the network. Round-trip time never moved off ~9 ms across roughly 137 ping/pong exchanges — every ping answered, so the socket was alive and bidirectional to the end, not merely un-closed.

Heartbeats prove a socket is alive; they do not prove it still delivers. A second run settled that by publishing only after the socket had already been open for an hour:

03:05:00 [hb2] alive 1h0m0s · outstanding_pings=0 · last_rtt=9ms
03:05:09 published 3 messages   journal: 3 entries, reconnects: 0

Delivered nine seconds past the one-hour mark, over the same socket. Not merely surviving idle — still doing its job at the far end of the hour.

The control is what makes that mean anything: 35 sockets, every one lasting 2 m 05 s. Not “about two minutes” — the same value 35 consecutive times. That is an edge timer, not a flaky network.

A trap worth recording: the control had to ask the server to stop pinging too. With the server heartbeating, even a client that never pings has frames arriving every 35 s — so the socket is not idle, and the control would have “passed” for reasons having nothing to do with the client.

Forced kill

kill -9 mid-stream, 10 messages published while the client was dead

  server messages : 20      DUPLICATED : 0
  client journal  : 20      LOST       : 0
  journal in order: True    PHANTOM    : 0

Replaying the same idempotency keys created no second message. The missed-pong severance was also exercised directly, with server-side fault injection that goes deaf while holding the connection open — the only way to reproduce the silent half-open socket that is the real risk. That put a number on something previously unstated: at a 35 s heartbeat a client can believe it is connected for 70–105 s after it is not. Under the ~100 s idle window, which is what the interval was chosen for, but it is the interval's real cost — and it is a server-driven dial rather than a constant.

R3

Vulkan, not ROCm — and a mistake worth keeping

The first pass built ROCm/HIP, found it correct — identical transcripts, 89% GPU utilisation, zero build errors first try — measured 14× realtime, and recommended it. Building Vulkan afterwards showed it is 4.8× faster, and that the HIP numbers had also inflated the CPU baseline by carrying ~3.2 s of ROCm initialisation into a measurement of the CPU path.

A backend that works and is 5× off the pace is a failure mode worth naming, because nothing about it looks like a failure. The first pass checked correctness and checked the GPU was genuinely used, and never checked whether the number was good.

ModelVulkanROCm / HIPCPU
base.en777 ms4044 ms2683 ms
small.en1007 ms4178 ms7298 ms
medium.en2045 ms5281 ms25595 ms

60 s Opus clip, Opus decode timed separately and included, median of 3. For base.en, HIP is slower than the CPU. Recommendation: Vulkan, small.en — and medium.en is now cheap enough to be a real option, which the HIP numbers would never have suggested.

R4

One schema, three languages, 41 shared vectors

web  41/41      dart 41/41      go  31 run, 10 skipped

quicktype — the only tool targeting both Dart and TypeScript from JSON Schema — unifies oneOf branches instead of emitting a tagged union. The fifteen frame types came out as one class with 30 fields, 28 of them nullable, in both languages. It also split Attachment into two differently-shaped classes named after where they appeared: schema drift inside a single generated file.

json-schema-to-typescript is genuinely good, but TypeScript-only and types-only. So the finding is the asymmetry, not the absence: a good TS generator paired with a bad Dart one produces two type systems of different shape from one schema, which is precisely the drift this gate exists to prevent. One zero-dependency generator now walks the schema once and emits all three.

Generated types make the clients agree about shape. They say nothing about whether an absent optional is omitted or nulled, whether an unknown attachment costs you the attachment or the whole message, whether a malformed timestamp is refused. None of those is a type error — which is why the 41 vectors matter more than the codegen.

Four things the schema had to decide that the spike had left open. The one worth your review: IDEA-23 specifies both a per-conversation seq and a scalar /sync?after=N, and those cannot both be true for a client with more than one conversation. Resolved as two ordinals — seq per conversation for ordering and unread, log_seq account-global as the only sync cursor.

R6

The Purser abstraction holds

connector.Connector accepts Catenary with no widening, no extra method and no side-channel. The per-device credential mismatch never reaches the boundary: at provisioning time the person has zero devices, so the only credential that can exist is a single enrolment token. Purser provisions people; Catenary tracks devices; they never exchange a unit.

The real finding is that Deprovision's fan-out makes it non-atomic, so the order is load-bearing. Revoke devices first and fail partway and you are left with an active account — the offboard failed open, and nothing in Purser's model can tell that from an offboard that never started. Disable first and the same failure leaves access genuinely gone, truthfully reported, and safe to retry.

Not derivable from a design review, which is why the gate asked for a stub. No Purser ticket needed — two doc notes on the existing contract instead.

R2

Push clears on two vendors

60 sends, zero misses, over roughly six hours — on real hardware, unplugged, in verified deep Doze, with the app evicted from memory.

DeviceDeliveredp50p90Max
Pixel 9 Pro31/310.86 s1.21 s6.07 s
Samsung SM-X23029/290.64 s0.92 s1.48 s

The Pixel finished the soak in genuine deep Doze with the probe decayed to standby bucket 40 (RARE) — aged out of every favourable bucket and still receiving. The Samsung was tighter than the Pixel at every percentile, so the vendor-optimiser worry that motivated testing it never materialised.

The 6.07 s outlier is the number to remember. Still “within seconds”, and nowhere near the four-minute failure the ticket warns about — but 6× the median. An occasional multi-second delay under deep Doze is normal on stock Android. Fine for chat; not fine for anything claiming real-time.

What actually went wrong was the instrument, three times

This gate cost far more time than the measurement warranted, and none of it was the system's fault: a callback whose errors were silently swallowed, a debug tool that bypassed the very bookkeeping being read as evidence, and Samsung's suppression of app logcat blinding the logging added to fix the first one. Each produced a confident zero from hardware that was working perfectly.

Treat “the measurement says zero” as a claim about the instrument until proven otherwise. A silent zero has the same shape as a working system with a broken observer — and this project produced that failure three times.

R5

Distribution, cleared on precedent

Friends install via the Play Store as a matter of policy, and Argosy and Lyceum already ship to them over the Play internal testing track — the exact path Catenary would use. The criterion is already demonstrated by two apps, with real recipients who did not build them.

Two findings made the alternative moot anyway. Google's Developer Verification means sideloading an unverified app now costs the recipient developer mode, a reboot and a 24-hour wait. And Samsung ships Auto Blocker on by default, which blocks installs from unauthorized sources and adb alike — found on the actual test hardware, not in documentation. Two independent obstacles, either of which fails the criterion alone.

Next

In order

  1. 01Sign off D1, or don't. Declining E2EE is what the spike calls the single decision separating a three-month project from a three-year one, with a very high reversal cost. Every gate is clear; this is the last thing between the spike and a verdict.
  2. 02Ratify or reject the seq / log_seq split. Every later phase is built on that shape, and it was my call rather than the spike's.
  3. 03Decide one client or two. R4 exists solely because D3 splits the client; a Capacitor-wrapped Vue app would delete that risk entirely, at the cost of a second mobile toolchain across the estate.
  4. 04Adopt the house codegen pipeline where it fits. Argosy already runs one OpenAPI spec to Go, TS and Dart. It covers the REST surface cleanly and pinches only on the WebSocket envelope.
  5. 05Close the Go validation gap. The server is the trust boundary and is currently the only implementation that would not refuse bad input.

Deliberately not done

No ticket transitions, no new tickets, no repo, no CTNR project — graduating early is the failure mode the spike names, and two gates are open. No Flutter client, because R4 comes first and now gives it a contract to generate against rather than a second hand-written copy of one. Nothing written into the Purser repo. The web client still uses its hand-written types.ts; migrating it is P1 work that would touch every component for no gain while there is still no transport.

Every claim here is reproducible from the working tree: ./verify.sh runs every check that does not need hardware.
